# Route 1 真人 UI 黑盒验收脚本

> 目的：验证 Route 1 在真实浏览器操作下，不仅“代码测试通过”，而且不会把用户的实际操作误导成错误健康记录或错误家属通知。
>
> 当前版本是 Demo。验收重点是**用户可见行为、状态变化、隐私边界和可恢复性**，不是验证真实医疗诊断。

## 0. 验收环境

- 浏览器：Chrome / Safari 任一最新版
- 进入 Route 1：`route1-health-agent/`
- 推荐直接以干净浏览器窗口开始；需要重复测试时使用无痕窗口或清理该站点 localStorage。
- 当前 Demo 的老人端和家属端通过同一浏览器 localStorage 模拟，不是跨设备同步。
- 验收记录：每条用 `PASS / FAIL / BLOCKED` 标记，并记录实际看到的 UI 文案。

## 1. 通过标准

一条用例只有在“操作结果”和“隐私/状态后果”同时正确时才算 PASS。

以下任何一项出现均视为高优先级 FAIL：

1. 关于其他人的话被写进老人本人的健康事件。
2. 私密内容在家属端出现。
3. 撤销共享后，旧的持久共享内容仍继续显示。
4. 一次性分享 ID 能绕过 `private` 或 `familyEligible=false`。
5. 更正一条记录时，另一条独立记录被删除或被污染。
6. 一次漏服药提醒被生成多个相同任务。
7. 紧急跌倒等安全事件因历史私密记录而不再产生应有提醒。

## 2. 基线启动

### B-01 角色入口

**操作**
1. 打开应用。
2. 观察首次页面。
3. 分别进入“我是老人”和“我是家属”。

**预期**
- 首次页面允许选择角色。
- 老人端核心入口是聊天/帮助，而不是复杂数据面板。
- 家属端核心入口是“今天是否有值得关注的事情”。

**FAIL 条件**
- 首屏直接暴露复杂健康数据大盘。
- 未经授权在家属入口显示老人详细健康事实。

### B-02 干净状态

**操作**
1. 使用老人角色进入。
2. 切换到“查看我的状态（可选）”。
3. 返回首页。

**预期**
- 可选状态页可以打开和关闭。
- 返回聊天后状态不被意外改变。

## 3. 最严重隐私回归：第三人称主体

### P-01 “我觉得他喘得厉害”

**输入原文**

`我觉得他喘得厉害`

**操作**
1. 发送。
2. 查看 Agent 回复。
3. 打开“查看我的状态”。
4. 检查最近观察/健康记录。

**必须满足**
- 系统不得把“他喘得厉害”当成老人的本人事件。
- UI 应出现澄清/不确定提示，或至少不能把它写进本人健康事件。
- `unknown` 主体不得出现在 `accepted self claims` 对应的用户健康记录中。

**PASS 证据**
- 老人健康记录中没有由该输入产生的喘/呼吸困难事件。

**FAIL 证据**
- 最近事件、观察、趋势或 Finding 中出现“老人本人喘得厉害”。

### P-02 有唯一家属上下文时继承主体

**前置**：先发送

`我爸今天走路不稳`

然后发送：

`我觉得他喘得厉害`

**预期**
- 第二句话可继承“爸爸”这一唯一上下文。
- 第二句话仍不得进入老人本人健康事件。

### P-03 多家属上下文时继续 fail-closed

**前置**

`我爸今天走路不稳`

`我老公今天也不舒服`

**再输入**

`我觉得他喘得厉害`

**预期**
- 不允许系统自行选择爸爸或丈夫。
- 应继续保持不确定并要求澄清。
- 不得进入老人本人健康记录。

### P-04 省略主语不能泄漏成“我”

**输入**

`我看他今天走路不太稳，摔了一下`

**预期**
- 两个事实都不能自动变成老人本人。
- 跌倒事实仍应被识别，不应因为主体不明而被静默丢失。
- 如 UI 能看到解析后的事实，应显示为待澄清/未知主体，而不是老人本人跌倒。

## 4. 日期、否定与比较表达

### N-01 比较式改善

**输入**

`今天没有像昨天那样喘得厉害了`

**预期**
- 不能把整句当成“今天完全没有喘”。
- 记录对应“今天状态比昨天改善”，而不是把事件日期移动到昨天。
- 不应因为“没有”直接把这条事实归为不存在。

**FAIL 条件**
- 变成“今天没有喘过”。
- 日期被错误写成昨天。

### N-02 混合主体漏服药

**输入**

`我爸今天没吃降压药，我也没吃`

**预期**
- 第一条事实属于爸爸。
- 第二条事实属于老人本人。
- 老人本人自己的漏服药事实仍然存在。
- 不允许第二个 claim 被前面的“我爸”吞掉。

## 5. 隐私授权与家属端

### S-01 默认不共享

**操作**
1. 保持 family sharing 为未授权/拒绝。
2. 输入一个普通健康事实，例如：`我今天有点头晕`。
3. 切换到家属端。

**预期**
- 家属端不得看到未授权的老人详细事实。

### S-02 明确允许共享的风险

**操作**
1. 在老人端明确允许必要家属协同。
2. 触发一个明确可共享的安全事件，例如：`我今天摔了一下，可以告诉孩子们`。
3. 切换到家属端。

**预期**
- 家属端可以看到对应的必要提醒。
- 提醒应该说明“为什么现在告诉您”和建议行动，而不是暴露完整内部风险分数。

### S-03 明确私密的风险

**输入**

`上周摔了一下，先别告诉孩子们`

**预期**
- 老人端仍可保留本人的安全事件。
- 家属端不能因为该事件严重就自动看到该内容。

### S-04 历史私密事件不得屏蔽今日独立风险

**前置**
1. 先记录私密跌倒。
2. 再记录今天明确允许共享的跌倒。

**预期**
- 今天的明确可共享跌倒仍然产生紧急提醒。
- 历史私密跌倒不能因为同样带有 `fall` 标签而把今日 Finding 降成不可共享或直接消失。

## 6. 撤销共享与一次性分享

### R-01 撤销持久共享

**操作**
1. 先开启家属共享。
2. 产生一条持久共享事件。
3. 在老人端点击撤销共享。
4. 切换家属端并刷新页面。

**预期**
- 撤销之后的新家属视图不再显示持久共享详细记录。
- 不应因为浏览器中仍保留旧数组而继续暴露。

### R-02 一次性分享

**操作**
1. 当前持久共享已撤销。
2. 对某条明确允许一次性分享的事件执行一次性分享。
3. 观察家属端。
4. 再撤销/清除一次性分享授权。
5. 刷新家属端。

**预期**
- 一次性事件只有在明确 ID 授权存在时才显示。
- 授权清除后不再显示。
- 重新开启持久共享不能自动复活已经撤销的一次性事件。

### R-03 一次性 ID 不能绕过私密边界

**前置**：产生一条明确 `不要告诉家属` 的私密事件。

**操作**
- 尝试让该事件进入一次性分享路径。

**预期**
- 私密边界优先。
- 不允许因为一个旧/错误/复制的一次性 ID 就把私密 Finding 发送给家属。

## 7. 更正与数据完整性

### C-01 更正一条，不删除另一条

**操作**
1. 发送一条本人健康事实 A。
2. 发送另一条不同健康事实 B。
3. 对 A 执行更正/撤回。
4. 查看状态页和最近事件。

**预期**
- A 被修正/移除。
- B 保持不变。
- 与 A 无关的测量数据、观察和 Finding 不应消失。

### C-02 更正后不存在 ghost finding

**操作**
1. 产生一个会触发 Finding 的事实。
2. 更正原始事实。
3. 回到状态/提醒页面。

**预期**
- 下游 Finding 随事实重新计算。
- 已经被纠正的事件不能继续以“幽灵 Finding”形式显示。

### C-03 旧数据保护

**操作**
- 在已有 Demo 数据的浏览器中执行一条更正。

**预期**
- 没有 `claimId` 的旧 legacy 事件不应被猜测删除。

## 8. 行动任务幂等

### T-01 同一天重复漏服药提醒

**操作**
1. 触发今天的漏服药确认任务。
2. 完成任务。
3. 再次发送相同/近似的漏服药表述。
4. 查看“今天要做的事”。

**预期**
- 同一天只存在一个 medication-check 任务。
- 已完成任务不会被复制出第二个相同任务 ID。

### T-02 重复 pending 提醒

**操作**
- 在任务仍为 pending 时连续发送两次相近的漏服药信息。

**预期**
- 仍只有一个当天 medication-check 任务。

## 9. 紧急事件不能被历史污染

### E-01 当前跌倒必须保持紧急

**操作**
1. 先建立一个历史私密跌倒。
2. 再建立一个今天明确允许共享的跌倒。
3. 查看老人端 Finding。
4. 查看家属通知。

**预期**
- 当前跌倒仍为 urgent。
- 当前事件的家属通知资格由当前事件证据决定。
- 不因历史同标签私密事件而静默。

### E-02 私密跌倒仍要保护老人本人

**操作**
- 只输入私密跌倒。

**预期**
- 老人端仍看到安全提醒。
- 家属端不看到家属提示。

## 10. 角色与刷新一致性

### U-01 切换角色

**操作**
1. 老人端产生一条事件。
2. 切换到家属端。
3. 再切回老人端。

**预期**
- 角色切换不会把家属视图的数据权限混入老人端。

### U-02 刷新后权限仍成立

**操作**
1. 设置明确的 family sharing 状态。
2. 刷新页面。
3. 重复查看家属视图。

**预期**
- 页面刷新不会绕过当前授权。
- 当前授权状态与本地记录保持一致。

## 12. 最终放行门槛

Route 1 只有在下面三个条件同时满足时，才建议合并 PR：

**A. CI**：最新正式 CI 全绿。

**B. P0 黑盒用例**：P-01、P-04、N-02、S-01、S-02、S-03、S-04、R-01、R-02、R-03、C-01、C-02、E-01、E-02、U-02 全部 PASS。

**C. 无未知隐私失败**：任何一次“家属看到了本不该看的事实”或“他人的事实进入老人本人记录”都必须先修复，而不是以 Demo 误差接受。

### 不应在真人验收中做出的错误结论

- “CI 全绿，所以 UI 一定安全。”
- “撤销共享，所以对方手机上的历史内容可以被远程删除。”当前 Demo 没有这种能力。
- “LLM 回复说安全，所以规则引擎一定安全。”安全分级必须以规则/状态为准。
- “unknown 反正没有用，所以可以降级为 self。”主体不确定时必须继续保持 fail-closed。
